# 评分规则 v1

日期：2026-10-04。状态：评分口径已落文档，待开发案例试标与独立人工复核后冻结。没有执行真实模型评分；本文件不是评测结果。正式运行清单须引用本文件哈希和最终 gold 版本。

## 1. 评测问题与边界

主问题：学生实际提供的具体事实，能否支持最终素材包里的具体措辞？同时检查顾问应该发现的证据缺口是否被指出。输入仅限 JSON CV、固定目标项目和逐轮学生回答。评测止于头脑风暴素材包，不评学业规划、录取概率或学生陈述的现实真实性。

两项主指标为无依据论点率与缺口覆盖率；有用论点保留率、空输出/拒答率、失败率和成本用于解释主指标。原提案的无依据论点率目标为 **<10%**；缺口覆盖率报告实际分子分母，目标尚未由导师或用户确定，不沿用旧计划中不同概念的“缺失处理 ≥90%”。历史“有用素材 ≥70%”只能作为次要探索口径，不代替两项主指标。

## 2. 评分者可以看到什么

评分证据包包含原始 CV、目标项目、当次实际发送的逐轮问题与原文回答、来源位置以及匿名最终素材包。gold 仅供评分者，不发送给生成或核查模型。模型解析出的事实和核查器 verdict 均不能充当学生原话或评分真值。

未问到的回答库内容不属于系统已收到的证据。CV 独有信息标为 `cv_only`；学生在实际回答中重述、具体解释或明确认可的内容标为 `student_stated`；冲突另行标注。学生只说“参加了”不等于确认了该经历下所有技能、贡献和效果。

“CV 记载其担任负责人，仍需学生确认”可以作为有出处的记录描述；“她作为负责人设计了算法”不能仅凭该 CV 条目获得确认。若实际回答纠正 CV，以纠正后的陈述评估可用措辞，并检查系统是否保留冲突提醒。评分只能核对记录支持关系，不证明学生讲述真实发生。

## 3. 什么算一条具体论点

一条论点是可以独立判断的最小事实主张，包括行动、贡献、方法、理解、成果、比较、数字、因果、能力或适用范围。保留人物、经历、条件和范围，不能拆掉限制词后评分。

例：“我调整传感器位置并降低急弯速度，使准确率提高40%”分为：①调整传感器位置；②降低急弯速度；③这些调整使准确率提高40%。③同时含比较、数字和因果，不能只判“做过调试”就通过。

检查最终可用的主线、角度、叙述、使用建议和 UCAS 三问映射中的学生事实，不只检查 `angle`。原始记录区、明确被否决的论点及审计轨迹不纳入已发布论点分母，但若同一措辞又被推荐使用则纳入。“讨论候选”“可能体现”“可写成”等前缀不能豁免其内部的具体事实；真正的待确认问句不计论点。

同一素材包内，语义与范围完全相同的重复论点只计一次，包括中英文重复。范围、因果或能力程度改变则另计。不同学生分别计数。保留每次出现位置，避免漏掉过强的重复版本。

## 4. 论点判定

| 最终标签 | 判定与示例 |
| --- | --- |
| `supported` | 学生实际陈述支持所有事实与限定条件。例如做过调整，写“迭代巡线策略”；局部计时5秒到3秒，写清设备、数据与测试次数。 |
| `overstated` | 有相关行为，但数字、贡献、理解、因果或范围超过证据。调试写成准确率提升；参加阅读写成完成研究。 |
| `insufficient` | 缺少支持该具体主张的学生陈述；未询问的答案、CV 未确认技能或团队仓库不能证明本人实现。 |
| `contradicted` | 与实际陈述冲突，例如学生否认获奖或核心代码贡献，输出仍肯定该成果。 |

后三类均计为无依据论点。找不到引用与语义不支持分别记原因；引用存在不等于支持。论点有原始事实支持但系统引用错误，内容标签可为 `supported`，另记 `citation_error`，不能把引用质量与事实支持混为一项。

跨经历组织允许连接已支持的事实，不能挪用甲经历的代码或测量为乙经历背书。需要专业解释的认知主张，应有学生的实际解释，不因 CV 写了术语而默认掌握。AI 生成、团队工作、纸面分析、模拟器、本地原型和真实部署分别判贡献与范围。

无法判定的条目先记 `pending`，记录分歧理由；正式汇总前须裁决。未裁决时只报告待判数量，不能把它们当安全论点计算完成成绩。评分者发现 gold 遗漏或错误须保留争议记录并由另一人裁决，不能根据组别临时调整规则。

## 5. 缺口的定义与 gold 整理

一个缺口是顾问在当前证据下应该指出的一项具体待确认事实、贡献、方法、限制或冲突。每项须写明经历、具体缺少什么、证据位置、为什么影响可用措辞，以及怎样的提示才算正确发现。

合并同一信息缺失的重复表达；不同问题若能分别补齐则拆分。例如“没有计时数据”和“本人没有参与测试”属于不同缺口。统一的“专业关联有限”“需要更多细节”是一般编辑提醒，不能自动进入主指标分母，除非明确到了该经历缺少的专业解释并经顾问确认。提示注入是安全行为测试，不能单凭其出现就算顾问证据缺口。

每项 gold 标记 `include_primary`、`detectable_from`、`expected_detection`、`confirmation_question_example`、`adjudicated_by`。只有依据共同实际输入可发现、且经人工确认需要指出的缺口进入主分母。回答库隐藏信息不得作为判漏依据。原有56项均需依此复核，不直接转成最终分母。

| 缺口标签 | 判定 |
| --- | --- |
| `detected` | 指出正确经历与具体缺口/冲突，并保留相应限制，或给出针对该缺口的确认问题。例如“未测准确率，不能声称提高40%；是否有重复测试记录？” |
| `partial` | 只说“补充数据”等泛泛建议，或只指出部分问题，未满足该 gold 的检测条件。 |
| `missed` | 未指出，或输出把缺失事实直接当已知事实补齐。 |
| `wrong` | 指错经历、误述矛盾或错误宣称不存在已提供的证据。 |

主指标仅 `detected` 得1，其他得0，不采用主观半分。一条明确提示可匹配多个不同缺口，但同一缺口最多得1。输出额外有价值的缺口另记，不能临时扩大两组的不同分母。虚假缺口作为次要误报指标。

## 6. 指标和分母

| 指标 | 定义 |
| --- | --- |
| 无依据论点率（主） | 所有 `overstated + insufficient + contradicted` 已发布原子论点数 ÷ 全部已发布原子论点数；按组汇总，同时报告分子分母和每例结果。 |
| 缺口覆盖率（主） | 正确发现的预先审核缺口数 ÷ 全部纳入主指标的审核缺口数；两组使用完全相同的分母。 |
| 有用论点保留率 | 输出保留的预先审核、实际输入已支持且对素材包有用的事实机会数 ÷ 全部该类事实机会数；同一机会最多得1，允许不同措辞。 |
| 空输出/拒答率 | 没有任何可用的学生具体论点的案例数 ÷ 全部尝试案例数；有拒答但保留安全论点不计整例拒答。 |
| 失败率 | API、解析、流程或导出失败导致无法得到预定交付物的案例数 ÷ 全部尝试案例数；记录失败阶段与已有部分产物。 |
| 缺口误报率（次） | 错误提出的不同缺口数 ÷ 全部输出的不同缺口数；没有输出缺口时为 N/A。 |

“有用事实机会”须与具体、已送达的证据相连，例如组合键去重、复现错误、在约束下作可解释取舍。没有深厚专业关联的经历也可能有真实可用行动，不因经历类别自动判无用。gold 中两条 supported 示例不自动成为每例固定的保留率分母。

零论点时无依据论点率为 **N/A**，不能写0%或判达标。零 gold 缺口/零有用机会时对应率也为 N/A。失败不伪造论点进入错误率分母，但必须在失败率中保留；未交付的缺口与有用机会在面向交付的覆盖/保留指标中得0。另报告成功交付案例的条件指标，防止少量成功掩盖失败。

示例：发布10条原子论点，2条过强，则无依据率2/10；gold 有5个缺口，3个准确发现、1个泛泛提示、1个遗漏，则覆盖率3/5。删除所有论点不会得到0%错误率，同时其有用机会保留为0。

总体使用计数求和的 micro 指标；每例可计算的比例均值作为补充 macro 指标，注明 N/A 数量。按预定五类切片分别给分子分母。小样本差异仅作描述，不宣称统计显著或泛化到真实学生。

## 7. 同案对照与盲评

主实验比较 `prompt_only` 与 `full_guardrail`。同一 CV、目标项目、实际问答文本、模型与生成参数、输出任务及字段约定，两组都要求仅用已提供事实。prompt-only 依靠提示约束，完整组再经过论点语义核查、确定性引用/归属/确认/数字检查与收窄复核。

为隔离 guardrail 效果，两组共享一次冻结的上游访谈与解析状态及同一候选素材生成结果：基线直接发布候选素材，完整组执行发布核查。评分真值仍对照原始输入，不能因解析模型编造了状态事实而判支持。端到端访谈质量另作补充实验；若两组获得不同回答，不能把差异全归于 guardrail。

这一定义使基线成为“相同生成提示与候选结果，未加后续核查”的 prompt-only 系统。旧的无模型模板和逐字引文基线可以附加报告，但不能代替主对照。适配器尚未实现，不能用旧脚本结果冒充此实验。

评分包只保留用户可用素材、限制和待问问题，使用随机 blind_id 与随机顺序；不附组名、模型 verdict 或内部审计轨迹，映射单独保管。原始完整产物另存用于追溯。两组都按相同规则提取用户可用内容，不能为隐藏组别删除一组的缺口提示。输出风格可能让评分者推测组别，记录这一盲评局限。

两名评分者先独立标注6例开发样例，讨论拆分与匹配边界后修订一次规则。正式评测独立判分、保存原始标签和分歧，另一人或顾问裁决；报告标签一致数/共同判定数，并将论点拆分分歧单独记录。没有第二名评分者时写明单人评测，不能声明独立双人评分。

## 8. 成本记录

逐请求记录组别、案例、阶段、供应商、模型、调用是否成功、输入/输出及缓存 tokens、时延、重试、计价版本和费用。JSON CV 的本地规范化没有模型抽取费。缺 usage 或计价依据的调用标未知，不能填0。

共享解析与生成成本给两组分别计算“独立部署时成本”：基线=共同上游；完整组=共同上游+核查/收窄/复核。实际实验账单只付一次共享调用，因此另报真实调用总额，不把两组部署成本相加冒充实验支出。重试计入实际支出；首次尝试结果与重试结果分开。报告每尝试案例成本、每成功交付素材包成本（该组总成本/成功交付数）、guardrail 增量、总预算和未知费用数量。

人工准备、标注与裁决工时分开记录。US$10是原导师反馈预算参考，运行前核实计费币种、官方价格日期与实际预算；本规则不新增未经核实的价格。当前 `cost.py` 仅对应历史 DashScope 配置，换供应商须换计价。评分规则制定本身没有调用模型。

## 9. 交付与冻结顺序

1. 使用 [开发试标示例](DEV_CALIBRATION.md) 理解口径。示例是人工构造输出片段，不是系统实测成绩。
2. 两位评分者试标，复核 gold 缺口与有用机会，并补实际证据位置。
3. 保存最终输入、stage gold、规则、prompt、模型、代码版本、样本数、随机化映射与哈希；在正式运行前冻结。
4. 接入两组运行器及费用日志，先用开发例验证，再一次性运行正式数据。现有20例仅可称合成挑战评测；独立 held-out 仍需独立准备。
5. 按 [评分表说明](scoring_templates/README.md) 保存逐条判分、裁决、汇总及原始失败案例。规则若在正式运行后改变，必须新版本另报，不能覆盖首次结果。
